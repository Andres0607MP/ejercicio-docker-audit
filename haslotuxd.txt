PARTE 1: Git local — preparar el repositorio
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Abre una terminal en la carpeta del proyecto:

   cd /home/andres/Documentos/SENA/5_Trimestre/Evidencia_21-7/labs/ejercicio-docker-audit

2. Revisa el estado de Git:

   git status

   Deberías ver los archivos pendientes de commit.

3. Verifica que .env NO esté en el commit:

   git status
   git diff --cached --name-only | grep .env
   (si NO devuelve nada, está correcto)

   git check-ignore .env
   (debe devolver ".env" → está ignorado ✓)

4. Preparar el commit:

   git add .
   git add .github/
   git add bandit.yaml
   git add .trivyignore
   git add requirements-dev.txt
   git add docker-compose.yml
   git add REPORT_PASO4.md

5. Haz el commit:

   git commit -m "Paso 4: Infraestructura y despliegue EC2 (docker-compose.yml)"

6. Haz push a GitHub:

   git push origin main

   IMPORTANTE: Debes hacer push a la rama "main" para que
   se ejecute el job "publish-dockerhub" y se publique la imagen.

PARTE 2: Verificar el workflow en GitHub
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

7. Entra al repositorio en GitHub:
   https://github.com/TU_USUARIO/ejercicio-docker-audit

8. Haz clic en la pestaña "Actions".

9. Deberías ver el workflow llamado "CI/CD Pipeline".

10. Si hiciste push a "main", el workflow se ejecuta automáticamente.

11. Jobs que aparecerán (en orden):

    - test (Pytest)                        ← tests unitarios
    - security-scan (Bandit)               ← escaneo de código
    - docker-build (Docker Build)          ← construcción de imagen
    - trivy-scan (Trivy Vulnerability Scan) ← escaneo de imagen
    - publish-dockerhub (Publish to Docker Hub) ← PUBLICACIÓN (solo push a main)
    - deploy-ec2 (Deploy to EC2)           ← DESPLIEGUE (solo push a main)

    ORDEN DE EJECUCIÓN:
    1. test y security-scan corren en paralelo
    2. docker-build espera a test + security-scan
    3. trivy-scan espera a docker-build
    4. publish-dockerhub espera a trivy-scan (solo push a main)
    5. deploy-ec2 espera a publish-dockerhub (solo push a main)

12. Un job con check verde ✓ = éxito.
    Un job con cuadro rojo ✗ = falló.
    Si falla algo, haz clic en el job y revisa los logs.

13. IMPORTANTE sobre la imagen:
    - docker-build construye una sola vez (Build Único)
    - docker save guarda la imagen como .tar artefacto
    - trivy-scan carga el .tar y escanea
    - publish-dockerhub carga el MISMO .tar y publica en Docker Hub
    - NO hay un segundo build

Cómo crear el Docker Hub Access Token
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

17. Entra a https://hub.docker.com
18. Haz clic en tu avatar → "Account Settings" → pestaña "Security"
19. Haz clic en "New Access Token"
20. Ponle un nombre: "github-actions"
21. Selecciona permisos:
    - read:packages ✅
    - write:packages ✅
    - delete:packages (opcional)

23. Copia el token COMPLETO (solo se muestra una vez)
24. NO lo compartas ni lo guardes en el repositorio

26. Haz clic en "New repository secret"

28. Valor: pega el token que copiaste
29. Haz clic en "Add secret"

30. Luego crea el otro secret:
    - Nombre: DOCKER_USERNAME
    - Valor: andresmancera
    - Haz clic en "Add secret"

31. Para verificar que los secrets existen:
    - Aparecerán en la lista con un ojo tachado 👁️
    - Haz clic en el ojo para ver/ocultar el valor
    - El valor NO aparece en logs de GitHub Actions

PARTE 6: Pull Request vs Push a rama principal
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

40. Pull Request (PR):
    - Trabajas en una rama: git checkout -b mi-rama
    - Haces commit y push: git push origin mi-rama
    - Creas un PR en GitHub (pestaña "Pull requests" → "New pull request")
    - El workflow corre: test, security-scan, docker-build, trivy-scan
    - El job "publish-dockerhub" NO se ejecuta en PRs
    - Si todos los checks pasan (verdes), puedes hacer merge

41. Push a rama principal (main):
    - git checkout main
    - git merge mi-rama (o directamente en main)
    - git push origin main
    - El workflow corre TODO incluyendo publish-dockerhub
    - La imagen se publica en Docker Hub

42. Recomendación:
    - Usa PRs para validar cambios
    - Solo haz push a main cuando todo esté verde
    - Siempre haz push a main cuando quieras publicar una imagen

PARTE 7: Qué hacer si algo falla
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

43. Si falla "test" (Pytest):
    - Ejecuta localmente:
      pip install -r requirements-dev.txt
      pytest -v
    - Corrige los tests que fallen
    - Commitea y haz push de nuevo

44. Si falla "security-scan" (Bandit):
    - Ejecuta localmente:
      bandit -r . -x './.venv,./venv,./.git' -c bandit.yaml
    - Si hay nuevos hallazgos reales, corrígelos
    - No uses "|| true" para ocultar errores

45. Si falla "docker-build":
    - Ejecuta localmente:
      docker compose build
    - Asegúrate de que el Dockerfile funcione
    - Verifica .dockerignore

46. Si falla "trivy-scan":
    - Ejecuta localmente:
      docker build -t mi-api:test .
      trivy image --scanners vuln --severity CRITICAL,HIGH \
        --ignore-unfixed --ignorefile .trivyignore mi-api:test
    - Si hay CVEs nuevas HIGH/CRITICAL con fix disponible:
      a) Actualiza dependencias en requirements.txt
      b) O agrega la CVE al .trivyignore con explicación
    - Las CVEs en .trivyignore son falsos positivos o base image

47. Si falla "publish-dockerhub":
    - Verifica que DOCKER_USERNAME y DOCKER_PASSWORD están creados
    - Verifica que el Access Token de Docker Hub es válido
    - Verifica que el push fue a "main", no a otra rama
    - Revisa los logs del job "publish-dockerhub"

48. Si el workflow NO aparece en GitHub:
    - Verifica que el archivo esté en: .github/workflows/ci-cd.yml
    - Verifica que el nombre del archivo tenga extensión .yml
    - Haz un nuevo push para forzar la detección

PARTE 10.5: Inicializar EC2 (comandos manuales)

  > Ejecuta estos comandos MANUALMENTE en tu EC2.
  > NO los ejecutes desde aquí.

  Paso 1: SSH a la instancia
    ssh -i <tu-clave.pem> <EC2_USER>@<EC2_PUBLIC_IP>

  Paso 2: Instalar Docker
    curl -fsSL https://get.docker.com | sh
    sudo usermod -aG docker $USER
    # Sal y vuelve a entrar (logout/login)

  Paso 3: Instalar Docker Compose
    sudo apt-get update
    sudo apt-get install docker-compose-plugin
    # Verificar:
    docker --version
    docker compose version

  Paso 4: Preparar directorio
    mkdir -p ~/deploy && cd ~/deploy

  Paso 5: Copiar archivos desde tu PC
    scp -i <tu-clave.pem> docker-compose.yml \
      <EC2_USER>@<EC2_PUBLIC_IP>:~/deploy/

  Paso 6: Crear .env en la EC2 (con credenciales reales)
    cat > .env << 'EOF'
    DB_HOST=mysql
    DB_PORT=3306
    DB_USER=appuser
    DB_PASS=<password-real>
    DB_NAME=legacydb
    MYSQL_ROOT_PASSWORD=<root-password-real>
    IMAGE_TAG=latest
    EOF

  Paso 7: Docker login (si imagen privada)
    docker login -u "andresmancera" -p "<access-token>"

  Paso 8: Levantar stack
    cd ~/deploy
    docker compose -f docker-compose.yml up -d

  Paso 9: Verificar
    docker compose -f docker-compose.yml ps
    docker compose -f docker-compose.yml logs -f app

PARTE 10.6: Deploy automático via GitHub Actions

  El workflow ahora incluye el job "deploy-ec2":

    1. Copia docker-compose.yml al EC2 (via appleboy/scp-action)
    2. SSH ejecuta: docker login → docker pull → docker compose up -d
    3. Solo corre en push a main (no en PRs)
    4. Depende de: test, security-scan, trivy-scan, publish-dockerhub

  Para que funcione, debes crear en GitHub Secrets:
    SERVER_HOST    → IP o DNS de la EC2
    SERVER_USER    → usuario SSH
    SERVER_SSH_KEY → clave privada SSH (contenido completo del .pem)

  El job NO hardcodea ninguna credencial.
  Las credenciales de Docker Hub se pasan como env vars seguras.

  NO se ejecuta el deploy hasta que configures esas secrets.

PARTE 10.7: Nginx Proxy Manager

  Puertos:
    80  → HTTP  (público, para Let's Encrypt)
    443 → HTTPS (público, tráfico cifrado)
    81  → Admin (localhost solo, NO público)

  Primer acceso (via SSH tunnel):
    ssh -L 8181:localhost:81 <EC2_USER>@<EC2_PUBLIC_IP>
    Abrir: http://localhost:8181
    Login: admin@example.com / changeme
    Cambiar password inmediatamente

  Configurar proxy:
    NPM UI → Proxy Manager → Add Proxy Host:
    - api.<domain>  → Forward IP: app, Port: 5050
    - dozzle.<domain> → Forward IP: dozzle, Port: 9999
    - kuma.<domain> → Forward IP: uptime-kuma, Port: 3001

PARTE 10.8: AWS Security Group

  ABRIR:
    22  → 0.0.0.0/0 o IP administrativa (SSH)
    80  → 0.0.0.0/0 (HTTP para NPM)
    443 → 0.0.0.0/0 (HTTPS para NPM)

  NO ABRIR:
    3306  (MySQL — solo red internal)
    5050  (API Flask — solo NPM proxyea)
    81    (NPM admin — solo localhost)
    9999  (Dozzle — solo NPM)
    3001  (Kuma — solo NPM)

PARTE 10.9: Certificados HTTPS (Let's Encrypt)

  NPM gestiona certificados automáticamente:
    1. DNS apuntando a IP EC2
    2. NPM → Proxy Host → Editar → SSL → "Request a new SSL Certificate"
    3. NPM solicita a Let's Encrypt
    4. Certificado guardado en volumen npm_letsencrypt

  NO inventar certificados ni claves.
  NO almacenar claves privadas en Git.

PARTE 10.10: Rollback

  Strategy: tags inmutables por commit SHA.

  Rollback:
    cd ~/deploy
    docker compose -f docker-compose.yml up -d IMAGE_TAG=<sha-anterior>

  El valor IMAGE_TAG sobreescribe el .env (usa ${IMAGE_TAG:-latest}).
